1. 总纲与兼容性原则

一句话目标
在不影响现有数据、现有评分结果、现有接口的前提下，把「桥跨」作为新的评定单元接入系统，使新标准「构件 → 桥跨 → 全桥」的评定链有实体承载；存量数据全部保留，旧评分结果可继续查看，新检查走新引擎。

1.1 三条铁律（所有改造步骤必须满足）

#原则落地要求
1新增优先于修改所有表结构变更一律 ADD COLUMN（可空、带默认值），禁止 DROP / MODIFY 现有列；新增实体用新表，不改旧表语义。
2旧数据零破坏迁移只做「读旧 + 写新增列」，不改动任何旧字段的值；旧 weight、deductPoints、构件分、部件分、全桥分原样保留。
3双轨并行可随时回退新评分引擎通过配置开关切换；旧引擎代码不删除，仅加 @Deprecated + 保留旧入口，切换失败一键回退旧路径。

1.2 现状基线（已核实代码事实）

  • 对象树：bi_object 用「祖先链」模式（ancestors 逗号分隔），层级靠 ancestors 长度推断，无 node_type 字段。
  • 现有层级：桥梁(根) → 评定单元(主桥/左幅引桥) → 三分层(上部结构/下部结构/桥面系) → 部件 → 构件。没有「桥跨」层。
  • 构件：bi_component.code 形如 R-1-1#桥面铺装（R=幅、中段=跨号、尾段=跨内序号），跨号仅隐含在编码文本中，无结构化字段。
  • 评分：ScoreServiceImpl（100 分扣分制）、ConditionServiceImpl（部件 t 值汇总）、BiEvaluationServiceImpl（三分层+全桥，硬编码 0.4/0.4/0.2 与界限 [95,80,60,40]）。
  • 硬编码层级判断（加层后必改的最大坑）：correctAllWeights() 用 ancestors.length - rootIndex == 2 判「第3层」；reassignComponentsFromOthers() 用 == 3 / == 4 判第三/四层；repairCountsFromSubtree() 用 level >= 4 判构件叶子；Mapper 里 selectChildrenByIdRemoveLeafNew 等用 p.level < 4。
⚠️ 真实库核对偏差（2026-10-04 已连库实测，落地脚本必须据此修正）
已连通后台 MySQL（60.205.13.156:3306 / bi，MySQL 8.0.42）逐项核实，以下 5 处与本文档早期假设不符，迁移脚本必须按真实数据编写：
  • ① bi_object 达 391 万行，远超「几百条结构节点」假设——绝大部分（深度 4~6 层约 300 万行）是病害构件的「多面定位」叶子（左侧面/右侧面/腹板/顶面/底面等），结构节点仅约几千。迁移脚本严禁全表遍历，必须按 name/node_type 精确筛出结构节点再操作。
  • ② 结构层名称为「附属设施」，非本文档早前写的「附属构造」。M1 回填 node_type=LAYER 的 name 匹配应为 ('上部结构','下部结构','桥面系','附属设施')。
  • ③ 桥型信息已存在评定单元 name 里（如「长江二桥-主桥（测试）(钢-混凝土组合拱桥)」「(梁式桥)」），M4 绑定 bridge_type 可从 name 解析，但需清洗「（测试）」等杂质。
  • ④ 构件跨号段实际到 28（非仅 1~9）；编码格式本身 100% 合规（R-<幅>-<跨>-<序>#名，抽查不符=0），解析逻辑无需改，但勿写死跨数上限。
  • ⑤ 根节点 7498 个（含大量「XX（测试）」桥）、评定单元约 5980 个——灰度试点桥与「权威跨数清单」须按此量级规划。
核心设计取舍（沿用方案A定稿）
复用 bi_object 树表，新增 bi_object 6 列 + 2 个新表（bi_span_evaluation 跨评定实体、bi_span_component_part 构件-桥跨-部件映射），不改 bi_component 表结构，不新建树表、不改 parent_id/ancestors 语义，从而把改造范围压到最小，且天然向下兼容。

3. 数据库 DDL（增量、可回滚）

设计要点
全部 ALTER TABLE ... ADD COLUMN，新列一律 可空 + 带安全默认值，保证旧 INSERT/UPDATE 语句不受影响；新实体用独立新表，旧 bi_evaluation 表结构不动。

3.1 bi_object 新增列

-- 1) 节点类型：旧数据一律回填默认值，不改变既有层级语义
--    描述 bi_object 结构树节点角色，与「构件」无关（构件在 bi_component 表，不带 node_type）
ALTER TABLE bi_object
  ADD COLUMN node_type VARCHAR(16) NOT NULL DEFAULT 'LEGACY'
    COMMENT '节点类型:ROOT/UNIT/SPAN/LAYER/PART/LEAF(结构对象末端/面定位)/LEGACY(旧数据占位)';

-- 2) 跨号：仅 SPAN 及跨下节点回填，其余 NULL
ALTER TABLE bi_object
  ADD COLUMN span_no INT NULL COMMENT '跨号，从1起；非跨内节点为NULL';

-- 3) 桥型代码：语义为「评定单元级」属性（B.1.1 桥型按桥梁划分、B.1.3 全桥统一权重），
--    绑定在 UNIT 节点，SPAN 冗余继承（须做一致性校验）
ALTER TABLE bi_object
  ADD COLUMN bridge_type VARCHAR(16) NULL COMMENT '桥型代码（附录B B01~B21），UNIT级绑定，SPAN继承';

-- 4) 结构层影响系数 γ（decimal 避免浮点误差，附录B含0.42/0.38等非整值）
ALTER TABLE bi_object
  ADD COLUMN gamma DECIMAL(6,4) NULL COMMENT '结构层影响系数γ，附录B按桥型';

-- 5) 桥跨附加属性（共用墩/全桥性构件/待确认标记等 JSON）
ALTER TABLE bi_object
  ADD COLUMN props_json TEXT NULL COMMENT '桥跨扩展属性JSON，如shared_pier/pending_confirm';
为什么加 gamma 而不是复用 weight
旧 weight 语义是「部件权重」（旧规范 0.4/0.4/0.2 校验依赖它），新标准「结构层 γ」与「部件 ω」是两个不同量，混用会污染旧数据。故 γ 独立成列，ω 未来另加 omega 列（本阶段可暂用 weight 承载部件 ω 的迁移映射，见 §4.4）。

3.2 bi_component 表：不加列

构件挂跨不落在 bi_component 上（重要修正）
早期方案曾在 bi_component 上加 span_id/span_no 两列，该设计有缺陷，已废弃。原因：
  • 单值外键表达不了多跨：共用构件（墩/支座/伸缩缝）在两跨均要计算，bi_component.span_id 只能存一个值，会退回「一个构件只能挂一个跨」的老路，与关系表的多对多语义直接冲突。
  • 制造数据不一致源头：若 bi_component.span_id 与关系表映射不一致，以谁为准无法界定，违反「单一事实来源」原则。
  • span_no 是冗余：跨号由关系表 span_id → bi_object.span_no 即可取得，无需在构件表重复存。
结论：「构件→桥跨」的归属关系，唯一权威来源是关系表 bi_span_component_part（见 §3.3b），bi_component 保持「构件实体」的纯粹性，只保留现有 bi_object_id（构件→部件，一对一）不动。

3.3b 新表 bi_span_component_part（构件-桥跨-部件映射）

为什么需要这张表（评定计算的硬需求，非归属冗余）
桥跨评定公式 BSCI(ij) = 100 − Σ CI(ij)·ω(j)·γ(j) / 5 要求引擎对跨内每个部件 j 求和，其中 CI(ij) 是「该部件下最差构件标度」、ω(j) 是「该部件的权重」。因此引擎必须能回答：这个构件，在本跨里，属于哪个部件（PART）节点、该部件的 ω 是多少。
  • 普通构件：构件只属于一个跨、一个部件，bi_component.bi_object_id（一对一）即可表达；此表只有一行。
  • 共用构件（桥墩/支座/伸缩缝，正式稿 3.3.1 条文说明「在两跨均要计算」）：同一物理构件同时属于两个跨，且在两个跨里对应的是两个不同的部件（PART）节点——单靠 bi_component.bi_object_id 一个外键存不下第二个跨的部件身份，必须用本表显式锚定 part_id。
一句话：bi_object_id 表达「构件→部件」的归属，part_id 表达「构件在该跨内以哪个部件参与评定」的计算映射，两者职责不同，缺一不可。 
-- 构件-桥跨-部件映射：共用构件跨级部件锚定，服务于 BSCI 评定计算
CREATE TABLE bi_span_component_part (
  id            BIGINT NOT NULL AUTO_INCREMENT COMMENT '主键',
  component_id  BIGINT NOT NULL COMMENT '构件ID(bi_component.id)',
  span_id       BIGINT NOT NULL COMMENT '桥跨节点ID(bi_object.id, node_type=SPAN)',
  part_id       BIGINT NOT NULL COMMENT '该构件在此跨内所属部件节点ID(bi_object.id, node_type=PART)',
  is_shared     TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否共用构件(相邻跨均计入,1=共用)',
  create_by     VARCHAR(64) DEFAULT '',
  create_time   DATETIME NULL,
  update_by     VARCHAR(64) DEFAULT '',
  update_time   DATETIME NULL,
  remark        VARCHAR(500) DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_component_span_part (component_id, span_id, part_id),
  KEY idx_span (span_id),
  KEY idx_component (component_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='构件-桥跨-部件映射(共用构件跨级部件锚定,服务于BSCI评定)';
命名与字段约定（已定稿）
  • 表名 bi_span_component_part：以「桥跨（span）为评定主轴」领起，表达「构件在某跨内的部件身份」这一三元关系。
  • 字段 part_id（非 object_id）：对齐方案A 节点类型体系里部件层的 node_type=PART 术语，精确指向「部件节点」，避免与 bi_object「泛指任意节点」混淆。
  • 保留 is_shared：虽可由「同一 component_id 跨多个 span_id」推导，但显式标记利于报告去重、共用构件人工复核清单，以及未来「共用但仅单边计分」等特殊处理；仅当 PART 层逐跨物理生成（§4.4 已钉死）时，part_id 在两跨必然不同，唯一键 (component_id, span_id, part_id) 天然保证一个构件在某跨只有一个部件身份。

4. 数据迁移脚本（幂等 + 校验）

迁移总原则
脚本必须幂等（重复执行不产生副作用）、分批提交、每步打印校验计数。用存储过程或应用内 Migration Runner 均可；以下给 SQL 骨架 + 应用侧解析逻辑分工。

4.1 阶段划分

阶段动作产出可重跑
M1 回填 node_type按现有 ancestors 深度 + 名称推断节点类型（详见下）每节点打上类型✅ 幂等
M2 生成 SPAN 节点按权威跨数清单生成 SPAN 节点，回填 bi_object.span_noSPAN 节点 + 跨号✅ 幂等
M3 构件挂跨（写关系表）解析 bi_component.code 提取跨号 → 写入 bi_span_component_part 关系表（component_id+span_id+part_id）构件×跨×部件映射✅ 幂等
M4 绑定 bridge_type/gamma按桥型人工/规则映射附录B参数到 SPANγ/ω 参数就位✅ 幂等
M5 校验全量核对：无孤儿、无重复跨号、层级一致性校验报告✅ 只读

4.2 M1：节点类型回填规则

-- 依据：parent_id=0 → ROOT
UPDATE bi_object SET node_type='ROOT' WHERE parent_id=0 AND node_type='LEGACY';

-- 评定单元：parent_id 指向 ROOT 的直接子节点
UPDATE bi_object o
  JOIN bi_object p ON o.parent_id=p.id AND p.parent_id=0
  SET o.node_type='UNIT' WHERE o.node_type='LEGACY';

-- 其余：暂按现有结构层识别（上部结构/下部结构/桥面系/附属设施 → LAYER；注意真实库名称是「附属设施」而非「附属构造」）
UPDATE bi_object SET node_type='LAYER'
  WHERE node_type='LEGACY'
    AND name IN ('上部结构','下部结构','桥面系','附属设施');

-- 部件层：父节点是 LAYER 的
UPDATE bi_object o JOIN bi_object p ON o.parent_id=p.id AND p.node_type='LAYER'
  SET o.node_type='PART' WHERE o.node_type='LEGACY';

-- 结构对象末端（面定位叶子）：无子节点的节点 → LEAF
-- 注意：这些是 bi_object 树的叶子（左侧面/右侧面/顶面/底面/倒角等），
--       不是构件；构件在 bi_component 表，通过 bi_object_id 挂载，不带 node_type
UPDATE bi_object o
  SET o.node_type='LEAF'
  WHERE o.node_type='LEGACY'
    AND NOT EXISTS (SELECT 1 FROM bi_object c WHERE c.parent_id=o.id AND c.del_flag='0');
M1 关键提醒
node_type 回填不改变任何层级，只是给现有节点「贴标签」，供后续加 SPAN 层时定位。旧代码若仍按 ancestors 长度判断层级，不会受影响——这正是「先贴标签、后加层」的兼容策略。

4.3 M2/M3：生成 SPAN + 构件挂跨（写入关系表）

推荐用应用侧 Java Migration（可复用已核实的 R-<幅>-<跨>-<序>#名称 规则），SQL 仅做辅助查询。核心逻辑伪代码：

// 解析构件编码：R-1-1#桥面铺装 → 幅=1, 跨=1, 序=1, 名=桥面铺装
Pattern P = Pattern.compile("^([A-Z])\\-(\\d+)\\-(\\d+)\\#(.+)$");

// 1. 用权威跨数清单确定每个评定单元(UNIT)的跨数 N，按 1..N 生成 SPAN 节点：
//    parentId = UNIT.id, name = "第"+spanNo+"跨", node_type='SPAN', span_no=spanNo
//    用 templateObjectId 引用模板（多跨不物理复制，见方案A）
// 2. 对每个构件解析出 spanNo（若编码不规范，标记 pending_confirm 待人工复核，不强行归跨）
// 3. 解析该构件在此跨内所属的部件(part_id)：普通构件取 bi_component.bi_object_id 对应 PART；
//    共用构件（墩/支座/伸缩缝）在两跨各对应不同 PART 节点
// 4. 写入关系表 bi_span_component_part(component_id, span_id, part_id, is_shared)
//    —— 不写 bi_component 表（构件表不加列）
// 5. 将 SPAN 的祖先链设为 UNIT 的 ancestors + UNIT.id

SQL 侧兜底（识别无法解析的构件编码，供人工复核）：

SELECT id, code, name, bi_object_id
FROM bi_component
WHERE del_flag='0'
  AND code NOT REGEXP '^[A-Z]-[0-9]+-[0-9]+#.*$';
⚠️ 「无病害 / 无构件」的跨不能靠构件编码推导——须引入权威跨数来源
桥跨是结构实体（SPAN 节点在 bi_object 中恒存在），与「有无病害」无关；但迁移时仅从 bi_component.code 枚举跨号会漏掉「无病害且历史上从未建过构件」的跨。因此 M2/M3 生成 SPAN 前，必须先用一个权威跨数清单（设计/竣工文件的跨径布置表，或人工确认的跨数）确定每个评定单元的跨数 N，再按 1..N 生成 SPAN 节点；构件编码解析仅用于「把已有构件挂到对应跨」，不用于「决定有哪些跨」。校验：生成后的 SPAN 跨号应覆盖 1..N 连续无缺号（缺失即漏跨，见校验7）。
共用构件 / 全桥性构件 / 无法解析构件的处置 （依据正式稿 3.3.1 条文说明、B.1.3 条文说明）
  • 共用构件两跨均计入（重要修正）：正式稿 3.3.1 条文说明明确「相邻两跨共用的桥墩、支座、伸缩装置等在两跨均要计算；拼宽结构中共用的拼接缝、横隔板等在各评定单元均要计算」。不再采用此前「归跨号较小一侧」的方案。构件挂跨的唯一载体是关系表 bi_span_component_part(component_id, span_id, part_id, is_shared)（DDL 见 §3.3b）：共用构件（墩/支座/伸缩缝）在表中有两行（两跨各一行），part_id 显式锚定「该构件在此跨内所属部件节点」，服务 BSCI 求和的 CI(ij)·ω(j)；is_shared=1 标记共用，服务报告去重与人工复核。
  • 全桥性构件（悬索桥主缆/索塔/锚碇）：单跨悬索桥整桥即 1 跨无歧义；多跨走 3.1.8 专用标准出口，构件不挂任何 SPAN，关系表中不出现该构件的任何行。
  • 无法解析编码：不写入关系表 + 构件 props_json={"pending_confirm":true}，绝不猜测，进人工复核队列。

4.4 M4：绑定桥型与 γ/ω 参数

子树复用策略（先定死，避免开发左右摇摆）
每个 SPAN 下挂一棵 LAYER(γ) → PART(ω) → LEAF(构件) 子树。因同 UNIT 内各跨桥型一致，子树划分相同，为防「30 跨 = 30 份重复节点」爆炸，采用三层混合策略：
  • SPAN：物理节点，每跨一条（评定链实体载体，承载 spanNo + 跨级部件清单）。
  • LAYER：γ 按桥型固定、跨间无差异 → 用 template_object_id 模板引用共享，不逐跨物理复制。
  • PART：ω 固定可共享，但「该跨是否设此部件」是跨级差异（B.1.3 未设部件取 0）→ 部件 ω 值查模板，「部件设置清单」必须逐跨独立记录。实现上 PART 可物理生成（每个 SPAN 下只建该跨实际设置的部件），或 PART 共享模板 + 用 props_json 记录跨级部件清单。推荐前者（物理生成实际部件），与 §4.4 下方「只生成实际部件」一致，引擎遍历最直观。
  • LEAF（构件）：物理，每跨独立，构件通过关系表 bi_span_component_part 挂跨（构件实例不同，不可共享）。
一句话：「跨」与「构件」物理，中间 LAYER 可模板复用，PART 以「逐跨实际部件」为准——既能控节点规模，又满足 B.1.3 的跨级部件差异。
  • 桥型绑定在评定单元（UNIT）级，SPAN 继承——不需要逐跨指定桥型，且同一评定单元内跨的桥型必然一致。依据：3.1.2「桥梁存在不同结构形式…拼宽时，宜将拼宽结构分别划分评定单元」——不同桥型本就应拆成不同评定单元，即「桥型边界 = 评定单元边界」；B.1.1 桥型按桥梁划分；B.1.3 异形桥参照类似桥型划分；正式稿 B.1.3 又规定「全桥各跨采用统一权值」。SPAN 上的 bridge_type 为继承冗余值，迁移后须校验「同 UNIT 下所有 SPAN 的 bridge_type 一致」（校验5），若有跨异型，说明评定单元划分有误，应拆 UNIT 而非改跨的 bridge_type。
  • gamma 回填到 SPAN 下的 LAYER 节点（上部/下部/桥面系/附属构造各自 γ，按桥型查附录B）。
  • 逐跨记录「部件设置清单」（哪些部件在该跨实际存在）：SPAN 下按附录B生成部件/构件节点时，只生成该跨实际设置的部件（缺省部件不建节点）。引擎按 B.1.3 条文说明处理：以「部件设置最完整的跨」为 ω 基准，其他跨未设部件的标度取 0（不扣分）。这是 3.3.1 公式求和范围（n=该跨组成部件数量）的直接依据。
  • 部件 ω：新增 omega 列承载新标准部件权重（0~100 整数），旧 weight 列保持旧语义不动（见下方兼容处理）。
ω 语义冲突的兼容处理
旧 weight（部件权重，0~1 小数，用于 0.4/0.4/0.2 校验）与新 ω（0~100 整数）冲突。为向下兼容，新增独立列承载 ω 更稳妥： 
ALTER TABLE bi_object ADD COLUMN omega INT NULL COMMENT '部件权重ω(附录B,0~100整数)';
这样 weight 保持旧语义不动，新引擎只读 omega，彻底隔离两套体系。

4.5 M5：迁移后校验 SQL

-- 校验1：构件总数不变（与备份基准比对）
SELECT COUNT(*) FROM bi_component WHERE del_flag='0';

-- 校验2：无孤儿SPAN（SPAN 在关系表中无任何构件挂接 → 异常）
SELECT s.id, s.name FROM bi_object s
WHERE s.node_type='SPAN' AND s.del_flag='0'
  AND NOT EXISTS (SELECT 1 FROM bi_span_component_part p WHERE p.span_id=s.id);

-- 校验3：同一评定单元内跨号不重复
SELECT parent_id, span_no, COUNT(*) c FROM bi_object
WHERE node_type='SPAN' AND del_flag='0'
GROUP BY parent_id, span_no HAVING c > 1;

-- 校验4：未挂跨的构件数（关系表中无记录的构件，应为0或仅全桥性构件/待确认项）
SELECT COUNT(*) FROM bi_component c
WHERE c.del_flag='0'
  AND NOT EXISTS (SELECT 1 FROM bi_span_component_part p WHERE p.component_id=c.id);

-- 校验5：同一评定单元下所有 SPAN 的 bridge_type 必须一致（桥型是 UNIT 级属性，SPAN 为继承冗余）
SELECT parent_id, COUNT(DISTINCT bridge_type) c FROM bi_object
WHERE node_type='SPAN' AND del_flag='0' AND bridge_type IS NOT NULL
GROUP BY parent_id HAVING c > 1;

-- 校验6：部件设置清单完整性——每跨的部件集合必须是该 UNIT 基准跨（部件最全跨）的子集

-- 校验7：每个评定单元的 SPAN 跨号须连续覆盖 1..N 无缺号（缺失=漏跨，尤其"无病害无构件"的跨）
SELECT parent_id, COUNT(*) AS span_count, MIN(span_no) AS min_no, MAX(span_no) AS max_no
FROM bi_object
WHERE node_type='SPAN' AND del_flag='0'
GROUP BY parent_id
HAVING span_count <> (max_no - min_no + 1);

5.3.1 新评分引擎核心约定（SpanEvaluationService 实现必读）

部件取最差构件标度，构件数量不参与计算
依据正式稿 3.2.5 / 3.2.6 / 3.3.1（符号定义：CI = max{ECI}，j=同类构件数量、n=部件数量、ω=部件权重）：
  • 构件级：ECI = EDI + EFI + EAI（标度加法，≥5 取 5）。EDI = max(耐久性标度 0~2, 结构性标度 0~3)；EFI 0~2；EAI -1~1。构件等级按 ECI∈{0,1,2,3,4,≥5} 映射 1~5 类。
  • 部件级（PART）：CI = max{该部件下所有构件 ECI}，取最差构件标度，不按构件数量加权、不取平均。
  • 结构层（LAYER）：结构指数 = 100 − Σ(CI·ω)/5，求和范围为该层组成部件（n=部件数量）。
  • 桥跨（SPAN）：BSCI = Σ(结构指数·γ) = 100 − Σ(CI·ω·γ)/5，γ 为结构层影响系数。
关键约定（向下兼容）：新引擎不消费 count 字段——构件数量不进权重、不进分母（旧标准 4.1.2 的 t 值按构件数折减已废除）。count 保留仅服务于旧引擎与报告/追溯；n（部件数量）由 LAYER 下挂的 PART 节点数天然表达，无需单独字段。
⚠️ 最高风险点：硬编码层级判断
全仓库搜索 ancestors 长度、rootIndex、level < 4、== 2/3/4 等模式，逐一确认是否受加层影响。加 SPAN 层后所有层级 +1，这些判断若不改为按 node_type，会导致权重修正、构件重分配、数量回算全部错位——这是整个改造工作量最易低估、最易出回归的地方。务必用 grep -rn "rootIndex\|level < 4\|length - rootIndex\|== 3\|== 4" 全量排查。

6.2 灰度策略

  1. 阶段0（默认）：engine=legacy，系统行为与改造前完全一致（新列默认值 + 空值不影响旧逻辑），旧数据、旧结果、旧接口全部不变。
  2. 阶段1（影子运行）：新引擎只计算不落库，输出新旧结果对比日志，人工核对差异（重点：跨号归类、γ/ω 取值、界限边界值）。
  3. 阶段2（按项目灰度）：选定 1~2 座试点桥切 engine=span，新旧结果并存，人工复核无误。
  4. 阶段3（全量切换）：全局切 engine=span，旧引擎保留但不再用于新检查；存量旧结果仍可查询。
兼容性关键
「影子运行 + 按项目灰度」确保任何一步异常都能立即切回 engine=legacy，无需回滚数据。数据迁移（§4）与引擎切换（§6）解耦——迁移可先行完成并长期保持 idle 状态，不影响线上。
