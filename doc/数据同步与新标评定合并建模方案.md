# 数据同步与 2026 新标评定合并建模方案

> 文档版本：v1.6
> 最后更新：2026-10-04
> 定位：离线同步线 + 新规范桥跨评定线「彻底合并」后的顶层数据模型设计
> 依据：`数据同步文档索引.md`、`APP 离线同步开发指南.md`、`后端数据同步开发指南.md`、`doc/20260930/` 下 6 份新规范分析设计文档，以及真实库 `bi` 实测核对

## 1. 背景与目标

### 1.1 为什么要合并

离线同步（App 采集 → 服务端落库）与 2026 新规范桥跨评定（BSCI 引擎）是同一业务的两条改造线。若不合并，会出现**断层**：

> 离线端采的是「旧 4 层结构」的数据，线上 BSCI 引擎要的是「桥跨主轴 + 构件↔跨↔部件」的新标数据，两边模型对不上，采集的数据线上算不了。

### 1.2 现场采集场景（本次设计的核心输入）

用户在**现场**用 App 完成以下动作，这些动作是权威数据来源，必须一路传到后端：

1. 选定一座桥 → 选定某个**评定单元 / 桥幅**（UNIT）
2. 指定该桥幅有 **N 跨**（权威跨数，现场录入）
3. 逐跨指定：这一跨**有哪些部件**（墩 / 支座 / 伸缩缝 / 桥面铺装 …）
4. 在部件下采集**构件**、**病害**、附件
5. 离线暂存 → 同步上传 → 服务端重建 SPAN/PART 树 → 落 `bi_span_component_part` → BSCI 评定

### 1.3 两条已拍板的设计决策

| 决策点 | 结论 |
|---|---|
| 桥跨数 / 部件清单的权威存储 | **存 `bi_object` 树节点本身**（现场录入直接生成 SPAN/PART 节点），不设独立配置表 |
| 离线端模型形态 | **完整树形结构**（离线 `bi_object` 也带 `node_type`/`span_no`，与后端同构） |

这两条决策带来一个根本性好处：**同步时「零转换映射」**——离线树节点直接映射为后端树节点，跨数、部件清单就是树本身，评定引擎直接读树，无第二事实来源。

### 1.4 数据三层次模型（本轮核心认知）

现场采集涉及的数据分**三个层次，性质不同，同步方向与外键策略不同**：

| 层次 | 表 | 性质 | 同步方向 | 离线端标识策略 |
|---|---|---|---|---|
| 台账 / 分发 | `bi_project` / `bi_task` / `bi_building`（含其 `bi_object` UNIT 根节点） | **下发只读**（后端预分配，App 不新增） | 服务端 → App | **整数 id 直通**（服务端 id 下发，不加任何 uuid 列） |
| 结构树 | `bi_object`（UNIT 根节点为下发只读；SPAN/PART/LAYER 为采集生成） | **混合** | 下发 + 上行 | 主键统一 `offline_uuid`；下发 UNIT 另带 `server_id` 整数作下行定位锚 |
| 采集结果 | `bi_component` / `bi_disease` / `bi_disease_detail` / `bi_attachment` | 采集生成 | App → 服务端 | `offline_uuid` |

**核心规律一句话**：外键**指向「下发只读数据」用整数 id 直通**（服务端 id 已下发到 App）；外键**指向「采集生成数据」用 `offline_uuid`**（App 端无服务端 id）。`bi_object` 例外——它主键统一 `offline_uuid`（消除「下发整数 id 与采集自增 id 同表撞车」），下发 UNIT 节点靠额外 `server_id` 列做下行定位，表内父子引用统一 `parent_uuid`。**下发只读表（project/task/building）本身不加任何 uuid 列。**

#### 1.4.1 下行分发模型（project / task / building）

- `bi_project`（266 条）→ `bi_task`（16411 条，已绑 `building_id`+`project_id`）→ `bi_building`（13368 条），典型的「一个项目分发出大量任务」预分配形态；
- **每个 App 用户有自己独立的 SQLite 数据库**，`bi_project_user`/`bi_task_user` 只是服务端用来「决定给该用户下发哪些 task」的**服务端私有表**，**不进离线数据库**（用户 SQLite 里本就只有自己的数据，无需再记分配关系）；
- **App 端 SQLite 里 project/task/building 已有关联好的记录**，用户只从中**选择** task 开始采集，**不会新增 task**；
- 因此这三张表是**下行数据**，离线端主键 id 直接存服务端整数 id，`bi_disease` 等采集数据用整数 `task_Id`/`building_id`/`project_id` 直通。

#### 1.4.2 关键复用事实：building 与 task 是 N:M

同一座桥可被多个 task 复用（实测 `building_id=1861` 关联 14 个 task）。故 `bi_disease` 需同时存 `building_id` + `project_id` + `task_Id` 三件套，才能区分「同一座桥哪一次检测采的病害」。

#### 1.4.3 building 与其 object 根节点同事务生成

**后端新建 building 时，在同事务里往 `bi_object` 插入一条记录（评定单元节点，`node_type=UNIT`，name 形如「株山湖中桥(梁式桥)」），并设置好 `offline_uuid`，`bi_building.root_object_id` 指向这条记录的 id。** 因此下发生成时 UNIT 节点**同时具备整数 id 与 `offline_uuid` 两套标识**。

- 这条 UNIT 根节点是**下发只读**数据（在 `bi_object` 表里：主键 `offline_uuid` + `server_id` 存整数 id）；
- App 用户在它**下面**新增 SPAN/PART 等采集节点（`offline_uuid`，`server_id=NULL`）；
- `bi_building` 用整数 `root_object_id` 直通定位 UNIT 根节点（**不需要 root_object_uuid**，见 §2.3b）；
- 特大桥会拆成「主桥 + 左右幅引桥」等多个 building（评定单元），它们各自的 UNIT 根节点挂在同一个「整桥」父节点下（实测「龙桥特大桥-主桥」的 root_object parent_id=246818，即整桥节点）。

## 2. 后端 MySQL 模型修改方案

### 2.1 总原则（开闭原则）

只增不改、旧表旧列零破坏、新表独立、双轨可回退。所有改动 = **加列 + 新表**。

### 2.2 `bi_object` 加列（结构树承载新标语义）

```sql
ALTER TABLE bi_object
  ADD COLUMN node_type     VARCHAR(16) NOT NULL DEFAULT 'LEGACY'
    COMMENT '节点类型:ROOT/UNIT/SPAN/LAYER/PART/LEAF(结构对象末端)/LEGACY(旧数据占位)',
  ADD COLUMN span_no       INT NULL COMMENT '跨号,从1起;仅SPAN及跨下节点有效,其余NULL',
  ADD COLUMN bridge_type   VARCHAR(16) NULL COMMENT '桥型代码(附录B B01~B21),UNIT级绑定,SPAN继承',
  ADD COLUMN gamma         DECIMAL(6,4) NULL COMMENT '结构层影响系数γ(附录B,含0.42/0.38非整值)',
  ADD COLUMN omega         INT NULL COMMENT '部件权重ω(附录B,0~100整数,与旧weight隔离)',
  ADD COLUMN props_json    TEXT NULL COMMENT '扩展属性JSON(共用墩/全桥性构件/待确认等标记)';
```

> 复用现有 `template_object_id` 做多跨模板引用（LAYER 跨间无差异，用模板共享，不逐跨物理复制）。
> `omega` 独立于旧 `weight`（旧 weight 是 0~1 小数、用于旧 0.4/0.4/0.2 校验），彻底隔离新旧权重体系。

### 2.3 `bi_object` 加同步字段 + UUID 外键（服务离线端）

离线端无服务端自增 ID，用 UUID 表达「采集生成数据之间的引用」。同步落库时经 `uuidMap` 转为整数 ID：

```sql
ALTER TABLE bi_object
  ADD COLUMN offline_uuid   VARCHAR(64) NULL COMMENT '离线UUID-4,同步唯一标识',
  ADD COLUMN is_offline_data TINYINT(1) NOT NULL DEFAULT 0 COMMENT '0=云端/下发,1=离线生成',
  ADD COLUMN offline_deleted TINYINT(1) NOT NULL DEFAULT 0 COMMENT '0=正常,1=已删除',
  ADD COLUMN parent_uuid    VARCHAR(64) NULL COMMENT '父节点offline_uuid(采集节点挂采集父节点用)';
```

> **不加 `building_id`，也不加 `building_uuid`**：building 与 object 保持现状的**单向关联**——`bi_building.root_object_id → bi_object.id`，且「一棵树一套」（每个 building 的 root_object 是独立子树根）。object→building 的归属靠 `root_object_id` 反向（或解析 `ancestors` 第 2 段）得到，object 侧**不新增任何 building 外键列**，维持模型最简、符合开闭原则。
> `parent_uuid` 承载离线树节点间的父子引用（统一，无双轨）：离线端 `bi_object` 主键为 `offline_uuid`，故父引用一律记父节点的 `offline_uuid`。同步落库时经 `uuidMap` 转为整数 `parent_id`（下发 UNIT 节点已在 uuidMap 预置 `offline_uuid→server_id` 映射）。

### 2.3b 下发只读表不加任何 uuid 列（整数 id 直通）

`bi_project` / `bi_task` / `bi_building` 是**下发只读**数据（后端预分配，App 只选择、不新增），**不加任何 uuid 列**，整数 id 直通：

- 离线端这三张表的主键 `id` 直接存服务端整数 id（下行时原样下发）；
- `bi_disease` 等采集数据用整数 `task_Id`/`building_id`/`project_id` 直通（这些整数外键已存在）；
- 无「App 端新生成、需 uuid 标识」的 project/task/building 记录，故无 uuid 需求。

> **关键澄清（v1.6 拍板）**：`bi_building` 也**不需要 `root_object_uuid`**——building 找 UNIT 根节点用整数 `root_object_id` 直通即可（UNIT 节点是下发只读数据，其整数 id 已下发到 App，存于 `bi_object.server_id`）。「离线 `bi_object` 主键改 uuid」解决的是 `bi_object` 表**内部**下发整数 id 与采集自增 id 撞车的问题，与 building 的指针无关。
> `bi_task` 已有 `building_id`/`project_id` 整数外键（分发时已绑定），离线端直接用。
> `bi_project_user`/`bi_task_user` 是**服务端私有表**（决定每个用户 SQLite 装哪些 task），不参与离线同步、无需加列。

### 2.4 `bi_component` 加列（仅加同步字段，不加挂跨列）

```sql
ALTER TABLE bi_component
  ADD COLUMN offline_uuid     VARCHAR(64) NULL,
  ADD COLUMN is_offline_data  TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN offline_deleted  TINYINT(1) NOT NULL DEFAULT 0;
```

> **不加 `span_id`/`span_no`**：构件可属多跨（共用构件），单值外键表达不了多跨，构件挂跨唯一载体是关系表 `bi_span_component_part`。`bi_component.bi_object_id`（构件→部件，一对一）保持不动。

### 2.5 采集业务表加同步字段（对齐既有 20260409 脚本命名）

采集生成的表：`bi_disease` / `bi_disease_detail` / `bi_attachment`（`bi_building` 属下发只读，见 §2.3b）。加列分两类——**同步通用 3 列**（`offline_uuid`/`is_offline_data`/`offline_deleted`）+ **挂载 UUID 列**（对齐既有离线同步脚本命名）：

```sql
-- bi_disease：3 通用列 + object_uuid/component_uuid 挂载列
ALTER TABLE bi_disease
  ADD COLUMN offline_uuid     VARCHAR(64) NULL,
  ADD COLUMN object_uuid      VARCHAR(64) NULL,   -- → bi_object.offline_uuid
  ADD COLUMN component_uuid   VARCHAR(64) NULL,   -- → bi_component.offline_uuid
  ADD COLUMN is_offline_data  TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN offline_deleted  TINYINT(1) NOT NULL DEFAULT 0;

-- bi_disease_detail：3 通用列 + disease_uuid 挂载列
ALTER TABLE bi_disease_detail
  ADD COLUMN offline_uuid     VARCHAR(64) NULL,
  ADD COLUMN disease_uuid     VARCHAR(64) NULL,   -- → bi_disease.offline_uuid
  ADD COLUMN is_offline_data  TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN offline_deleted  TINYINT(1) NOT NULL DEFAULT 0;

-- bi_attachment：3 通用列 + offline_subject_uuid 挂载列
ALTER TABLE bi_attachment
  ADD COLUMN offline_uuid     VARCHAR(64) NULL,
  ADD COLUMN offline_subject_uuid VARCHAR(64) NULL, -- → 被挂载主体(病害等)的 offline_uuid
  ADD COLUMN is_offline_data  TINYINT(1) NOT NULL DEFAULT 0,
  ADD COLUMN offline_deleted  TINYINT(1) NOT NULL DEFAULT 0;
```

> **`bi_disease` 的挂载字段分两类**（外键策略核心体现）：
> - 指向**下发只读数据** → 整数直通：`task_Id` / `building_id` / `project_id`（这些字段**已存在**于 `bi_disease`，离线端直接用服务端整数 id，无需新增 UUID 列）；
> - 指向**采集生成数据** → `offline_uuid`：`bi_object_id`（→ object 树）、`component_id`（→ component），离线端以 `object_uuid`/`component_uuid` 表达，同步时经 uuidMap 转整数。
>
> **与既有脚本对齐**：`object_uuid`/`component_uuid`/`disease_uuid`/`offline_subject_uuid` 均为 `sql/20260409_offline_sync_ddl.sql` 已定义的命名，本方案沿用，不另起别名。

> ⚠️ **命名坑**：同库「任务 ID」字段有三种写法——`bi_disease.task_Id`（大写 I 驼峰）、`bi_task_user.task_id`（小写）、`bi_task.id`（主键）。同步映射与代码必须显式区分，勿混用。

### 2.6 新建关系表 `bi_span_component_part`（构件↔跨↔部件，唯一权威）

```sql
CREATE TABLE bi_span_component_part (
  id            BIGINT NOT NULL AUTO_INCREMENT,
  component_id  BIGINT NOT NULL COMMENT '构件ID(bi_component.id)',
  span_id       BIGINT NOT NULL COMMENT '桥跨节点ID(bi_object.id, node_type=SPAN)',
  part_id       BIGINT NOT NULL COMMENT '该构件在此跨内所属部件节点ID(bi_object.id, node_type=PART)',
  is_shared     TINYINT(1) NOT NULL DEFAULT 0 COMMENT '是否共用构件(相邻跨均计入,1=共用)',
  create_by     VARCHAR(64) DEFAULT '',
  create_time   DATETIME NULL,
  update_by     VARCHAR(64) DEFAULT '',
  update_time   DATETIME NULL,
  remark        VARCHAR(500) DEFAULT NULL,
  PRIMARY KEY (id),
  UNIQUE KEY uk_component_span_part (component_id, span_id, part_id),
  KEY idx_span (span_id),
  KEY idx_component (component_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='构件-桥跨-部件映射(共用构件跨级部件锚定,服务BSCI评定)';
```

> `part_id` 是评定计算硬需求（非归属冗余）：BSCI = 100 − Σ CI(ij)·ω(j)·γ(j)/5 要求引擎知道「共用构件在两跨各对应哪个部件、该部件 ω 是多少」。普通构件在此表 1 行，共用构件（墩/支座/伸缩缝）2 行（两跨各一行，part_id 指向各自跨下的 PART 节点）。

```sql
CREATE TABLE bi_span_evaluation (
```

### 2.8 同步基础设施表

> **P0 实测修正（2026-10-04）**：`bi_id_mapping`、`bi_sync_log` 已由既有 `sql/20260409_offline_sync_ddl.sql` 定义（该脚本未在目标库执行）。其结构与本方案早期草稿不同，**以既有脚本为准**，本方案不再重复建表，避免两套结构冲突：

```sql
-- ① offlineUuid → serverId 映射落库（既有 20260409 脚本定义，联合主键 table_name+offline_uuid）
CREATE TABLE bi_id_mapping (
  table_name   varchar(64) NOT NULL COMMENT '数据流经实体映射的基础表名',
  offline_uuid varchar(64) NOT NULL COMMENT '移动端分配的离线主键UUID',
  server_id    bigint(20)  NOT NULL COMMENT '服务端入库后的真实物理主键ID',
  create_time  datetime DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (table_name, offline_uuid),
  KEY idx_server_id (server_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='离线数据上行树状拓扑重解 ID 映射图';

-- ② 同步日志（既有 20260409 脚本定义）
CREATE TABLE bi_sync_log (
  id          bigint(20) NOT NULL AUTO_INCREMENT,
  sync_uuid   varchar(64) DEFAULT NULL,
  user_id     bigint(20)  DEFAULT NULL,
  status      int(11)     DEFAULT '0' COMMENT '0=进行中,1=成功,2=失败',
  client_info varchar(255) DEFAULT NULL,
  create_time datetime DEFAULT CURRENT_TIMESTAMP,
  finish_time datetime DEFAULT NULL,
  remark      text,
  PRIMARY KEY (id),
  KEY idx_sync_uuid (sync_uuid),
  KEY idx_user_id (user_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='离线数据同步审计日志表';

-- ③ 用户 SQLite 引用（本方案新增，P0 脚本已建）
CREATE TABLE bi_user_sqlite (
  id            BIGINT NOT NULL AUTO_INCREMENT,
  user_id       BIGINT NULL,
  minio_id      BIGINT NULL COMMENT 'SQLite文件MinIO ID',

```

> 映射表键设计差异说明：既有脚本用 `(table_name, offline_uuid)` 联合主键（同一 uuid 在不同实体表各自映射），本方案早期草稿用 `(entity_type, offline_uuid)` + 自增 id。二者等价，P0 采用既有 `table_name` 命名，`entity_type` 语义由 `table_name` 承载。

### 2.9 取消 `bi_object_component` 表

同步文档原设计的 `bi_object_component` 与 `bi_span_component_part` **语义重叠**（都在表达「构件属于哪个结构节点」）。决策：

- 构件→对象（粗挂接）→ 继续用 `bi_component.bi_object_id`；
- 构件→跨→部件（评定锚定）→ 用 `bi_span_component_part`；
- 同步载荷里的 `biObjectComponents` → 落库时按语义分流到上面两处，**不建独立表**。

## 3. 离线 App 端 SQLite 模型

### 3.1 设计原则

离线 SQLite 与后端 MySQL **同构**：`bi_object` 也带 `node_type`/`span_no`，现场录入直接生成完整树。同步时节点级零转换映射。

**关键约束**：离线 SQLite **只包含该用户相关的数据记录**（用户视角子集），不是全量库。因此：
- **下发只读表**（`bi_project`/`bi_task`/`bi_building`）存的是「分配给该用户」的记录，主键 `id` 直接存服务端整数 id；
- **采集生成表**（`bi_object`/`bi_component`/`bi_disease` 等）存的是「该用户现场采集」的记录，用 `offline_uuid` 标识。

### 3.2 下发只读表（离线版，整数 id 直通）

这三张表是服务端下行推给 App 的，App 端**只读、不新增**，主键 `id` 直接存服务端整数 id，**不加任何 uuid 列**：

```sql
-- 项目（下发）
CREATE TABLE bi_project (
  id                INTEGER PRIMARY KEY,          -- = 服务端 bi_project.id（直通）
  name              TEXT,
  year              INTEGER,
  code              TEXT,
  status            TEXT DEFAULT '0'
);

-- 任务（下发，已绑 building/project）
CREATE TABLE bi_task (
  id                INTEGER PRIMARY KEY,          -- = 服务端 bi_task.id（直通）
  building_id       INTEGER,                      -- = 服务端 bi_building.id（直通）
  project_id        INTEGER,                      -- = 服务端 bi_project.id（直通）
  type              INTEGER,
  status            TEXT DEFAULT '0'
);

-- 桥梁（下发）
CREATE TABLE bi_building (
  id                INTEGER PRIMARY KEY,          -- = 服务端 bi_building.id（直通）
  name              TEXT,
  area              TEXT,
  line              TEXT,
  status            TEXT DEFAULT '0',
  is_leaf           TEXT DEFAULT '1',
  root_object_id    INTEGER                       -- = 服务端 bi_object.id（UNIT根节点，整数直通）
);
```

> **不加 uuid 列（v1.6 拍板）**：三张下发表都是只读数据，整数 id 直通即可。`bi_building` 也**不用 `root_object_uuid`**——`root_object_id` 整数直通定位 UNIT 根节点（UNIT 是下发只读，其整数 id 已下发，存于离线 `bi_object.server_id`）。

> 分配关系表 `bi_project_user` / `bi_task_user` 是**服务端私有表**，**不进离线数据库**（每个用户有独立 SQLite，本就只装自己的数据）。

### 3.3 核心表 `bi_object`（离线版，混合：UNIT 下发 + SPAN/PART 采集）

> **主键策略（方案 X，2026-10-04 拍板）**：`bi_object` 是唯一「下发 + 采集」混合表，若用 `id` 自增主键，下发 UNIT 节点的服务端整数 id（如 246818）会与采集节点本地自增序列撞车。故离线端**统一用 `offline_uuid` 做主键**，`id` 退化为普通列 `server_id`。红利：`parent_id`/`parent_uuid` 双轨一并消灭，整表父子引用统一为 `parent_uuid`（因为 UNIT 节点下发时也带 `offline_uuid`，采集节点挂 UNIT 不再需要整数直通）。

```sql
CREATE TABLE bi_object (
  offline_uuid      TEXT PRIMARY KEY,            -- 统一主键：下发UNIT=服务端offline_uuid，采集节点=App生成
  server_id         INTEGER,                     -- 服务端整数id：仅下发UNIT节点有值；采集节点NULL(上行后回填)
  parent_uuid       TEXT,                        -- 父节点offline_uuid（UNIT/SPAN/PART 统一引用，无双轨）
  node_type         TEXT DEFAULT 'LEGACY',       -- ROOT/UNIT/SPAN/LAYER/PART/LEAF
  span_no           INTEGER,                     -- 跨号(SPAN及跨下节点)
  bridge_type       TEXT,                        -- 桥型代码(UNIT级)
  name              TEXT NOT NULL,
  order_num         INTEGER,
  template_object_id INTEGER,                    -- 模板引用(模板节点为下发数据，整数直通)
  props_json        TEXT,                        -- 扩展标记
  is_offline_data   INTEGER DEFAULT 1,           -- 采集节点=1，下发UNIT节点=0
  offline_deleted   INTEGER DEFAULT 0,
  create_time       TEXT,
  update_time       TEXT
);
```

> **关键：`bi_object` 是「混合性质」表**，两类节点的标识策略不同：
> - **下发的 UNIT 根节点**（building 建时同事务生成，服务端已设好 `offline_uuid`）：`offline_uuid` + `server_id` 双标识，`is_offline_data=0`，App 只读；
> - **采集生成的 SPAN/PART/LAYER 节点**：`offline_uuid` 标识，`server_id=NULL`，`is_offline_data=1`。
>
> **父子引用统一 `parent_uuid`**（无双轨）：无论是「采集节点挂下发的 UNIT/ROOT」还是「采集节点挂采集节点」（PART 挂 SPAN），父节点都已有 `offline_uuid`，一律写 `parent_uuid`。同步时服务端统一经 `uuidMap` 解析成整数 `parent_id`。
>
> **`server_id` 的作用**：仅用于「下行定位」——App 上传采集树时，靠下发 UNIT 节点的 `server_id` 让服务端知道「这批 SPAN/PART 挂在服务端哪条 UNIT 记录下」，避免服务端重复建 UNIT。它不是表内引用主键，不参与离线端内部关联。
>
> **无 `building_id` 列**：与后端同构，object 侧不存 building 外键，「object→building」靠 `bi_building.root_object_id` 单向反向定位（一棵树一套）。

```sql
  object_uuid       TEXT,                        -- 挂载的部件/对象UUID(part_uuid语义)
  name              TEXT NOT NULL,
  code              TEXT,                        -- R-<幅>-<跨>-<序>#名

```

### 3.5 关系表 `bi_span_component_part`（离线版，同后端）

```sql
CREATE TABLE bi_span_component_part (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  offline_uuid      TEXT,
  component_uuid    TEXT,                        -- 构件UUID
  span_uuid         TEXT,                        -- 跨节点UUID
```

### 3.6 采集结果表 `bi_disease`（离线版，整数直通下发数据）

```sql
CREATE TABLE bi_disease (
  id                INTEGER PRIMARY KEY AUTOINCREMENT,
  offline_uuid      TEXT NOT NULL UNIQUE,
  task_id           INTEGER,                     -- 整数直通：= 服务端 bi_task.id
  building_id       INTEGER,                     -- 整数直通：= 服务端 bi_building.id
  project_id        INTEGER,                     -- 整数直通：= 服务端 bi_project.id
  object_uuid       TEXT,                        -- 采集数据：→ bi_object.offline_uuid
  component_uuid    TEXT,                        -- 采集数据：→ bi_component.offline_uuid
  description       TEXT,
  type              TEXT,
  level             INTEGER,
  quantity          REAL,
  commit_type       INTEGER DEFAULT 1,
  is_offline_data   INTEGER DEFAULT 1,
  offline_deleted   INTEGER DEFAULT 0
);
```

> **关键差异**：`task_id`/`building_id`/`project_id` 是**整数直通**（指向下发的 project/task/building，服务端 id 已下发），`object_uuid`/`component_uuid` 是 **UUID**（指向采集生成的 object/component）。这是「整数直通下发数据、UUID 标识采集数据」原则的直接体现。
> 服务端落库时：整数三件套直接写 `task_Id`/`building_id`/`project_id`；`object_uuid`/`component_uuid` 经 uuidMap 转 `bi_object_id`/`component_id`。

### 3.7 现场录入动作 → 离线树节点的映射

| 现场动作 | 生成的离线节点 | node_type | 关键字段 |
|---|---|---|---|
| 选定任务（下发） | 复用下发的 bi_task | — | task.id 直通 |
| 选定桥（下发） | 复用下发的 bi_building + 其 UNIT 根节点 | UNIT（下发） | building.id / root_object_id 整数直通 |
| 选定桥幅 | 复用下发的 UNIT 根节点（或在其下新建） | UNIT | bridge_type |
| 指定 N 跨 | N 个 SPAN 节点（采集） | SPAN | span_no=1..N，parent_uuid 指向 UNIT |
| 指定某跨有某部件 | PART 节点（采集） | PART | 挂 SPAN 下（parent_uuid） |
| 采集构件 | bi_component 记录 + 关系表行 | — | part_uuid 指向 PART |
| 采集病害 | bi_disease 记录 | — | task_id/building_id 整数直通 |

## 4. 同步落库规则（零转换映射）

离线树节点 → 后端 `bi_object` 节点，字段一一对应。外键按「指向数据的性质」分两种处理：

| 离线字段 | 后端字段 | 转换方式 |
|---|---|---|
| offline_uuid | offline_uuid | 保留（采集节点） |
| parent_uuid | parent_id | 经 uuidMap（父节点无论下发 UNIT 还是采集节点，都有 offline_uuid） |
| server_id | （下行定位用，不落为表内引用） | 见下方说明 |
| node_type / span_no / bridge_type | 同名列 | 直接写入 |
| 关系表 component_uuid/span_uuid/part_uuid | component_id/span_id/part_id | 经 uuidMap（采集数据） |
| bi_disease.task_id/building_id/project_id | task_Id/building_id/project_id | **整数直通**（下发数据） |
| bi_disease.object_uuid/component_uuid | bi_object_id/component_id | 经 uuidMap（采集数据） |

> `parent_uuid` 统一经 `uuidMap` 转 `parent_id`：下发 UNIT 节点在 uuidMap 里**预置了 `offline_uuid → server_id` 映射**（下行时建立），故「采集节点挂 UNIT」与「采集节点挂采集节点」走同一条 uuidMap 解析路径，服务端落库逻辑统一。
> `server_id` 的作用是「下行定位锚」：App 上传采集树时带上父链顶层 UNIT 节点的 `server_id`，服务端据此确定采集子树挂在哪条已存在的 UNIT 记录下，不再建新 UNIT。它不落为表内引用字段。

> object→building 无显式外键，靠 `bi_building.root_object_id` 整数单向定位（一棵树一套），同步时采集节点随父链挂到 UNIT 根节点，归属自然确定。

**同步顺序**：

```
① 下行分发（服务端 → App）：project → task → building（连同其 bi_object UNIT 根节点，整数 id 存 server_id + offline_uuid 一并下发，并预置 uuidMap：offline_uuid→server_id）
② 上行采集（App → 服务端）：
   bi_object（多轮树处理：SPAN/PART 采集节点，parent_uuid 统一经 uuidMap 解析；下发 UNIT 节点靠 server_id 定位）
   → bi_component（object_uuid 经 uuidMap）
   → bi_span_component_part（component/span/part uuid 经 uuidMap）
   → bi_disease（task_id/building_id/project_id 整数直通；object/component uuid 经 uuidMap）
   → bi_disease_detail → bi_attachment
```

> `bi_project_user`/`bi_task_user` 不参与同步（服务端私有，仅决定每个用户 SQLite 下发范围）。
